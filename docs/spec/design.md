# Lean webhook notification system and operations dashboard

## 1. Purpose and scope

A locally runnable, one-day implementation of the [Benji senior engineer take-home](https://even-foxglove-53c.notion.site/Sr-Software-Engineer-380b9f151bae81218487d84c42741d17): register endpoints with event-type subscriptions, publish events, deliver signed HTTP webhooks with bounded retries, replay failures, and observe delivery live in an operations dashboard. This lean design builds on the earlier Benji specification and its agreed contracts — endpoint-owned subscriptions, HMAC-signed delivery, exponential retry with replay, and server-generated event IDs with a separate submission key — while re-deriving the product shape with a minimal endpoint model (no workflow, version, cutover, or archive layer), a single FastAPI process with an in-process worker, and SQLite as the durable queue.

Fixed constraints: one fixed local customer, loopback-only networking, no external infrastructure, Python backend, Vue 3 + TypeScript dashboard.

**Status terms:** **Required** comes from the assignment. **Chosen** was approved by Dror in the design review on 2026-09-27. This document is frozen once Dror approves the written version; changes require his explicit approval.

## 3. Domain model

| Entity | Fields | Invariants |
| --- | --- | --- |
| Endpoint | id, name, url, event_types (list), secret, enabled, created_at | URL is server-generated (`{receiver_origin}/webhooks/{id}`) unless explicitly provided, and passes FR-08 at creation; event_types nonempty; id immutable; secret never returned after creation |
| Event | id (server-generated), idempotency_key, type, payload (canonical JSON bytes), created_at | id generated by server; idempotency_key unique among events; payload ≤ 32 KiB canonical UTF-8 |
| Delivery | id (stable), event_id, endpoint_id, status, due_at, cycle_attempts, lease_expires_at, created_at, updated_at | Unique `(event_id, endpoint_id)`; retries and replay never change the delivery id |
| Attempt | id, delivery_id, number (monotonic per delivery), started_at, finished_at, outcome, response_excerpt | Number strictly increases across retries and replay cycles; excerpt ≤ 1 KiB |

Delivery statuses: `pending`, `in_progress`, `retrying`, `paused`, `succeeded`, `failed`. `succeeded` and `failed` are terminal until a replay of `failed` returns it to `pending`.

Single fixed customer is implicit; no customer table and no browser-supplied customer identity.

## 4. Behavior contracts

**FR-01 Intake and identity — Chosen.** `POST /api/events` validates key/type/payload, then in one transaction creates the event plus one delivery per enabled matching endpoint. The server returns `201` with the generated event id and `deduplicated=false`. A repeat with the same idempotency key and canonical-equal type/payload returns `200` with the original event id and `deduplicated=true`, creating nothing. Same key with changed type or payload returns `409 idempotency_conflict` without modifying the original. A different key with identical content creates a new event. No matching endpoint still persists the event with zero deliveries. When a submission requests schema enforcement, the payload is validated against the registered schema for the event type before anything is persisted; a violation returns `400 validation_error` with field paths only, creates no event, and does not consume the idempotency key. Event types without a registered schema keep the structural checks. *(Amended 2026-09-28 with Dror's approval.)*

**FR-02 Routing and fan-out — Chosen.** Each endpoint owns its subscriptions. Acceptance matches the event type against every enabled endpoint's `event_types`, across all endpoints. Each match persists exactly one delivery. Disabled endpoints are excluded. Persist before any outbound HTTP.

**FR-03 Disable and resume — Chosen.** Disable sets `enabled=false`, excludes the endpoint from new fan-out, and moves its `pending`/`retrying` deliveries to `paused` with their due time retained. An HTTP attempt already in flight may finish: success stays `succeeded`; a retryable failure becomes `paused`; a terminal failure stays `failed`. Resume sets `enabled=true` and restores `paused` deliveries: overdue work is due immediately, future work keeps its due time, attempt budget unchanged. Disable does not delete or rewrite history.

**FR-04 Automatic attempts — Chosen.** The first attempt is due immediately. A 2xx response succeeds. Transport errors, the 2-second total timeout, HTTP 408/429, and 5xx retry with exponential backoff: 2 seconds before attempt 2, 4 seconds before attempt 3, measured from the prior attempt's completion, three attempts maximum per cycle. Other non-2xx responses fail terminally. Redirects are not followed; 3xx is terminal. Each attempt records start/end, outcome class, HTTP status when present, and at most 1 KiB of response text. Backoff delays are configurable for tests; the 2s/4s defaults are the demonstrated behavior.

**FR-05 Worker and recovery — Chosen.** The worker claims due work with a 10-second lease using an atomic conditional update; at most four HTTP attempts run globally and one per endpoint. A claim interrupted by a crash becomes eligible after lease expiry; its attempt is recorded as `interrupted` and counts against the current cycle's three-attempt budget. With budget left it retries the same delivery; otherwise the delivery becomes `failed` and is replayable. Event acceptance never waits for outbound HTTP.

**FR-06 Replay — Chosen.** Replay starts a new cycle of up to three attempts on the same logical delivery, keeps all prior attempts and the same delivery id, and schedules the next attempt immediately. Replaying anything other than a `failed` delivery returns `409 replay_unavailable`. A delivery paused by disable cannot be replayed until resumed. Concurrent replay requests yield at most one new cycle.

**FR-07 Signed requests — Chosen.** Each endpoint receives a cryptographically random 32-byte secret, displayed once as `whsec_` + unpadded base64url. Every attempt sends the stored canonical event bytes as the body and headers `X-Webhook-Delivery-Id`, `X-Webhook-Timestamp` (Unix seconds), and `X-Webhook-Signature` (`v1=` + lowercase hex HMAC-SHA256). The signed message is UTF-8 `{timestamp}.{delivery_id}.` followed by the raw body bytes. The receiver compares signatures in constant time, rejects malformed headers and timestamps outside ±300 seconds, and deduplicates side effects by delivery id (in memory). Replay uses a fresh timestamp and signature with the same delivery id.

**FR-08 Destination policy — Chosen.** Endpoint URLs are validated at creation and revalidated at dispatch against the configured receiver origin (default `http://127.0.0.1:9000`): scheme `http`, exact configured host and port, path `/webhooks/{segment}` with one URL-safe segment `[A-Za-z0-9._-]{1,64}`, no credentials, query, or fragment. The sender generates the URL as `{receiver_origin}/webhooks/{endpoint_id}` when the client omits one; an explicitly provided URL is validated the same way. Receiver administration routes are excluded. Redirects are never followed. Rejection is a validation error at creation and a terminal dispatch-policy failure at delivery time.

**FR-09 Limits and errors — Chosen.** The idempotency key is 1–128 and the event type is 1–64 case-sensitive ASCII letters, digits, `_`, `-`, or `.`; payload is any JSON object or array up to 32 KiB canonical UTF-8, optionally validated against the event type's registered schema when enforcement is requested. API errors share `{code, message}` with codes `validation_error` (400, including payload-schema violations), `idempotency_conflict` and `replay_unavailable` (409), `not_found` (404), `internal_error` (500). Errors never include secrets, payloads, or internal traces. Rate limiting is cut (section 12). *(Clause amended 2026-09-28 with Dror's approval.)*

**FR-10 Live observability — Chosen.** The dashboard polls the API every 2 seconds while the tab is visible. State is authoritative on the server; the client never invents delivery outcomes. After a polling failure the client retains the last known state, shows a stale banner with the last successful update time, and resumes automatically.

## 5. API surface

| Method and path | Behavior |
| --- | --- |
| `POST /api/endpoints` | Create an endpoint from a name and event types; the receiver URL is generated server-side (an explicitly provided URL is validated per FR-08); `201` returns the endpoint plus its one-time secret |
| `GET /api/endpoints` | List endpoints without secrets, including `enabled` |
| `POST /api/endpoints/{id}/disable` / `enable` | Apply FR-03; return updated endpoint |
| `POST /api/events` | FR-01; `201` created, `200` deduplicated, `409` conflict |
| `GET /api/events?limit=` | Recent events with per-event delivery status counts |
| `GET /api/events/{id}` | Event with its deliveries (status, due time, attempt count) |
| `GET /api/deliveries/{id}` | Delivery, event payload, endpoint summary, ordered attempts |
| `POST /api/deliveries/{id}/replay` | FR-06; `202` accepted, `409` unavailable |
| `GET /api/overview` | Failed count, retrying count + earliest due, latest event summary |
| `GET /api/health` | Liveness/readiness probe |

## 6. Components and data flow

| Component | Responsibility |
| --- | --- |
| `backend/app/main.py` | FastAPI app, routes, lifespan starts/stops the worker |
| `backend/app/store.py` | SQLite schema and every query/transaction; one authoritative rule per business behavior |
| `backend/app/worker.py` | Claim → sign → send → record loop, concurrency limits, lease recovery |
| `backend/app/signing.py` | Secret generation and HMAC computation/verification helpers |
| `backend/app/models.py` | Pydantic DTOs and the error envelope |
| `backend/app/config.py` | Env-validated settings (`BENJI_DB_PATH`, `BENJI_RECEIVER_ORIGIN`, ports, retry delays) |
| `receiver/app.py` | Demo receiver: secret-keyed config page, any `/webhooks/` path, signature verification, in-memory log |
| `frontend/src/api/client.ts` | Typed HTTP only; `ApiError` distinguishes API errors from transport failures |
| `frontend/src/state/*` | Composable stores: async loading, polling, staleness, action transitions |
| `frontend/src/components/*` | Presentational components consuming state |
| `tests/` | pytest unit and integration tests against a real receiver instance |

Data flow: browser → `POST /api/events` → one store transaction (event + deliveries) → response; worker tick (~0.5s) claims due deliveries atomically, signs and posts via httpx (2s timeout, no redirects), records attempts and next due time; browser polls overview/events/delivery every 2s. SQLite in WAL mode is the queue; a restart recovers by sweeping expired leases. No broker, no external service. The receiver keeps its configuration and dedupe memory in process only; after a receiver restart the operator reconfigures it, and this limit is stated in the README.

## 7. Security requirements

- **SEC-01:** Boundary validation everywhere data enters: URL policy (FR-08), key/type/payload bounds, JSON parse errors, unknown ids.
- **SEC-02:** SSRF containment for the local demo: only the configured loopback receiver origin and documented `/webhooks/` paths, revalidated at dispatch, redirects refused. Production would require public HTTPS policy with resolved-address pinning; the local policy fails closed.
- **SEC-03:** Secrets are generated with `secrets.token_bytes(32)`, returned exactly once, never logged, never in list/read projections or frontend bundles, and compared in constant time at the receiver.
- **SEC-04:** All payload and response text is rendered as escaped text/JSON, never HTML. Response excerpts are bounded at 1 KiB in storage and display.
- **SEC-05:** API error responses use the safe `{code, message}` envelope without stack traces, secrets, or raw payloads.
- **SEC-06:** Services bind loopback only. There is no login; the single fixed customer and no browser-supplied identity are explicit local limits, not production claims.
- **SEC-07:** Production gaps are documented, not implied: authentication/RBAC, secret rotation, retention/redaction policy, per-endpoint rate limits, destination allowlists with DNS validation.
- **SEC-08:** Dependency surface stays minimal and pinned (FastAPI, uvicorn, httpx, pydantic, pytest; Vue, Vite, TypeScript, Vitest); no external fonts, CDNs, or telemetry.

## 8. Dashboard design

Event-centered journey view built on a shared design system (cards, status pills, Benji-inspired palette navy/vivid purple, system font stack) with a read-only Vue Flow canvas for the fan-out.

- **Header:** `Needs attention` (failed count), `Retrying` (count + earliest due), stale-state indicator.
- **Composer:** event-type select with Benji-domain examples (`reward_transaction_created`, `campaign_updated`, `member_account_linked`) plus custom input; JSON payload editor; generated idempotency key that rotates after each accepted event unless manually edited (manual reuse demonstrates deduplication and conflict); buttons disabled while pending; dedup and conflict notices; a pre-publish hint showing how many enabled endpoints currently subscribe, warning when none do.
- **Events list:** type, id, age, and delivery status counts with a `no receivers` chip for zero-delivery events; selecting an event opens the fan-out.
- **Fan-out:** the selected event as a source node with one endpoint node per delivery (status pill, attempt progress, last HTTP outcome with an inline `?` explanation for failed or retrying branches, animated edge only while an attempt is active), auto-layout with pan/zoom and no editing operations; `No receivers matched` for zero deliveries.
- **Delivery panel:** endpoint and URL, state, due time, a vertical attempt timeline (dot color per outcome, attempt number, HTTP status with a per-attempt `?` explanation of what that status means in context, duration, bounded excerpt, and the next scheduled attempt while retrying), formatted payload as escaped JSON, replay button only when eligible.
- **Endpoints panel:** create form (name and event types; the receiver URL is generated), one-time secret display with copy and receiver setup steps, enable/disable toggles.
- **States:** loading, empty, pending-action disablement, inline safe errors, dedup/conflict, stale banner, paused. Polling every 2s while visible per FR-10.

## 9. Testing strategy

- **Unit (pytest):** canonical-JSON identity, key/type/payload validation, destination policy, signature computation/verification, retry classification and backoff schedule, status transitions.
- **Integration (pytest, real HTTP):** the API plus worker against a real receiver (uvicorn on a free port, temp SQLite): fan-out counts, concurrent same-key dedupe, unique `(event_id, endpoint_id)` under concurrency, fail-once retry with observed backoff, three-attempt exhaustion, replay keeps delivery id and appends attempts, disable pauses/resumes and blocks replay, expired-lease recovery after restart, receiver signature acceptance/rejection, destination rejection. Tests override retry delays for speed; defaults 2s/4s are asserted in the schedule unit test.
- **Frontend (Vitest):** API error mapping, composer pending/dedup/conflict/uncertain states, polling staleness, replay gating, empty/loading rendering.
- **Browser (Playwright, chromium):** `python3 scripts/run_e2e.py` boots the receiver, API/worker, and dashboard on free ports with a temporary database and fast retry delays, then runs `frontend/e2e`: endpoint lifecycle and one-time secret, fan-out with deduplicated resubmission, live retry to delivered without refresh, verified failure history and replay on the same delivery, tampered-signature rejection, disable/no-match routing, and empty/pending/stale states.
- **Manual walkthrough:** documented in the README; success, fail-once, always-fail, replay, signature rejection, and dedup via browser and receiver page.

## 10. Acceptance criteria

- **AC-01:** Creating an endpoint returns its secret once; later reads and all diagnostics omit it.
- **AC-02:** A shared event type produces one delivery to each of two enabled subscribers; a single-subscriber type produces one; an unmatched event persists visibly with zero deliveries.
- **AC-03:** Resubmitting a key with canonical-equal content returns `200` with the original event id and no new deliveries, including under concurrency; changed content under the key returns `409` without altering the original; a fresh key with identical content creates a new event id.
- **AC-04:** Concurrent submissions, retries, and replay never create a second delivery for the same `(event_id, endpoint_id)`.
- **AC-05:** A fail-once receiver succeeds on attempt 2; repeated retryable failures produce attempt 3 after the 4s delay and end `failed`; a 404 fails terminally without retry.
- **AC-06:** Valid signatures pass; tampered body, delivery id, signature, malformed headers, and stale timestamps fail at the receiver.
- **AC-07:** Replaying `failed` keeps the delivery id, appends attempts, and appends a new cycle; replay of any other state returns `409`; a disabled endpoint's delivery cannot be replayed until resumed.
- **AC-08:** Disabling an endpoint stops new routing and pauses its queued deliveries; resume restores them without resetting the budget; in-flight attempts may finish; history is retained.
- **AC-09:** With the dashboard open, delivery state changes appear without manual refresh; a polling outage shows a stale banner and recovers automatically.
- **AC-10:** A delivery shows its payload and every attempt with outcome, timing, and bounded response text; a timeout is labeled outcome-unknown rather than failure-at-receiver.
- **AC-11:** Killing the sender mid-attempt leaves an `interrupted` attempt after restart; the delivery resumes within budget or becomes a replayable failure.
- **AC-12:** URL creation rejects non-loopback hosts/ports, foreign paths, credentials, query, and fragments; dispatch revalidates and never follows redirects.

## 12. Cuts and production gaps

Cut from this attempt: multi-tenant authentication and RBAC, rate limiting, editing endpoint URL/subscriptions after creation, workflow/version/cutover/archive concepts, secret rotation, configurable retry jitter, SSE/websockets (polling chosen), cross-browser matrix (chromium only), load testing, distributed workers, external queues. Production design would revisit each: authenticated customer scope, public HTTPS destination policy with DNS/IP validation, managed secret storage and rotation, tuned backoff with jitter, retention and redaction policy, horizontal dispatch with a real broker, and measured capacity targets. Local evidence never implies production readiness.
